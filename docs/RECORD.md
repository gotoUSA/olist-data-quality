# 기록: 검사, replay, 분석 결과

Olist 공개 데이터(주문 99,441건)로 데이터 품질 검사 기준을 먼저 정하고, 자동 검사와 오류 주입 테스트를 만든 뒤, 배송 지연과 리뷰 점수의 관계를 분석했다. 기준과 이유는 `CRITERIA.md`, 결정마다의 대안과 대가는 `DECISIONS.md`(D1~D36)에 있다.

## 요약

- 검사 19개(C0~C18)를 만들었다. 본 분석에 쓰는 열을 보는 관문 검사 6개(C0, C1, C4, C11, C17, C18)는 모두 통과했다.
- 오류 주입 테스트 22개로 각 검사가 넣은 오류를 정확한 건수로 잡고, 허용 범위 안의 값은 잡지 않는지 확인했다.
- 검사 과정에서 분석 계획을 바꾼 발견이 4개 있었다. 가장 큰 것은 택배에 넘긴 뒤 도착 기록이 없는 주문 1,094건으로, delivered만 보는 계획이었다면 가장 늦은 주문이 통째로 빠졌다.
- 예상 도착일보다 늦게 온 주문의 리뷰 평균은 2.3점, 예상 도착일까지 온 주문은 4.3점이다. 1~2점 비율은 62%와 9%다. 미리 정한 민감도 분석 5개와 5개 권역에서 방향이 같았다.

## 진행 순서

1. 후보 숫자를 SQL로 세고(`sql/profile_candidates.sql`), 검사마다 기준, 처리, 이유를 문서로 정했다. 리뷰 점수는 이 단계에서 보지 않았다.
2. 분석 방법(지연 정의, 구간, 비교 방법, 민감도 묶음, 보고 자릿수)을 결과를 보기 전에 고정했다.
3. 기준을 검사 코드로 만들었다(`checks/`). 관문 검사가 실패하면 종료 코드 1을 내고 분석이 멈춘다.
4. raw를 복사한 스키마에 오류를 넣고 검사가 잡는지 테스트했다(`tests/`).
5. replay 백테스트로 운영 환경처럼 날짜순으로 흘리며 월별·일별 경고를 돌렸다(`checks/replay.py`).
6. 분석을 돌렸다(`analysis/run.py`). 분석은 검사를 먼저 실행하고, 관문 실패나 검사가 요구한 민감도 누락이 있으면 멈춘다.

## 계획을 바꾼 발견

1. **분석 끝 날짜(D2).** 리뷰 작성일이 2018-08-31에서 끝난다. 설문은 도착일이나 예상 도착일에 나가므로, 예상 도착일이 그 뒤인 주문은 일찍 도착해야만 데이터에 들어온다. 실제로 그런 주문 1,998건 중 늦은 주문은 0건이었다. 그래서 예상 도착일이 2018-08-31 이전인 주문만 분석했다.
2. **미도착 shipped 1,094건(D26).** 택배에 넘겼고 예상 도착일이 지났는데 도착 기록이 없다(예상일에서 중앙값 207일 경과). 늦은 집단의 약 16% 크기다. 분실인지 기록 누락인지 데이터로 가릴 수 없어 본 결과에는 넣지 않고, 늦음으로 넣은 결과를 민감도 4로 함께 보고했다.
3. **늦음 여부가 갈리는 리뷰 39개(D36).** 리뷰 하나가 여러 주문에 붙었는데 그중 일부만 늦었다. 어느 주문을 평가했는지 알 수 없어 본 결과에서는 뺐다. 39개가 모두 늦은 집단으로 들어가고 극단 점수라면 1~2점 비율이 0.61%p 움직여 허용 폭(0.5%p)을 넘으므로, 늦음으로 넣은 결과를 민감도 5로 고정했다.
4. **좌표 범위(D32).** 브라질 본토 경계 상자로는 42행이 밖으로 나왔는데, 그중 11행은 실제 영토인 페르난두지노로냐 섬이었다. 상자를 대서양 섬까지 넓혀 31행만 오류로 셌다.

허용 폭은 데이터가 아니라 보고 형식에서 정했다. 평균은 소수 첫째 자리, 비율은 정수 %로 보고하므로, 최악의 경우에도 보고 숫자가 반올림 한 칸 넘게 움직이지 않는 건수를 관문 기준으로 썼다(D25).

## replay 백테스트

준비 기간 2017-01~06은 기준선에만 쓰고, 2017-07~2018-08을 날짜순으로 돌렸다. 기준선은 지난달까지의 데이터로만 계산했다(D34). 결과 전체는 `reports/replay.md`에 있다.

| 검사 | 경고 |
|---|---|
| C1 월별(포아송 P < 1%) | 2018-06(3건, 기대 0.16), 2018-07(3건, 기대 0.36) |
| C4 월별 | 2017-07(10건, 기대 1.67) |
| 예상일 지난 미도착 shipped 월별 | 2018-03(133건, 기대 82) |
| C6 월별 | 2017-12, 2018-01 |
| C15 일별 | 운영 실패 13일, 경고 11일(2018-04-20~23, 2018-07-03~04 승인 멈춤 포함) |
| C16 일별(지난 14일 중앙값 대비 2배 이상, 0.5배 이하) | 16일(블랙프라이데이 2일, 데이터 끝부분 8일 포함) |

C1의 2018-06·07은 전 기간 비율을 기준선으로 쓰면 잡히지 않았다(P 1.48%, 1.52%). 그 두 달을 기준선에서 빼면 잡히지만, 이상해 보이는 달을 빼서 이상하다고 판정하는 순환이 된다(D8). replay는 지난달까지만 기준선으로 쓰므로 두 달을 빼지 않고도 경고했다. 기준선 사건이 0건이라 판정을 보류한 달은 없었다.

## 한계

- 결론은 관계다. 늦은 주문의 리뷰가 낮다는 것까지 말할 수 있고, 지연이 리뷰를 낮췄다는 인과는 이 분석으로 말할 수 없다. 교란 변수는 권역 층화로만 일부 통제했다.
- 검사 기준 일부(C5의 60일과 3건, C15의 3시간과 12시간, C16의 2배, replay 준비 기간 6개월)는 같은 데이터를 보고 정했다. 그래서 이 검사들이 이미 알던 사건(2017-09-19 일괄 도착 처리, 승인 멈춤)을 잡은 것은 검사 성능의 근거로 쓰지 않는다. 분석 결론에는 영향이 없다. 결과를 만드는 규칙(지연 정의, 구간, 비교 방법)은 리뷰 점수를 보기 전에 정했고, 이 기준으로 주문을 뺀 민감도 1에서도 결과가 같다. 시간을 나눠 확인한 결과는 아래 '시간 분할 확인'에 있다.
- 지연 정의를 정하기 전에 배송 일수 구간별 리뷰 평균을 본 적이 있어, 완전한 사전 고정은 아니다. 예상일 대비 늦음과 리뷰의 관계는 분석 전에 보지 않았다.
- replay는 최종 상태 하나를 날짜순으로 흘린 것이다. 그날 시점에 실제로 보였을 상태(나중에 채워진 도착일 등)를 재현하지 못한다.
- 원인을 확정하지 못한 것: 승인 기록이 멈춘 날, 2017-09-19 일괄 도착 처리, 미도착 shipped가 분실인지 기록 누락인지, C9의 덜 낸 39건. 데이터에 원인 기록이 없다.

## 시간 분할 확인

같은 데이터로 기준을 정하고 평가하면 잘 맞는 것이 당연하다. 그래서 2017년 데이터만으로 기준을 다시 계산해 지금 기준이 그대로 나오는지 보고, 2018년에서 어떻게 동작하는지 셌다. 기준을 정할 때 이미 전체 데이터를 본 뒤라 완전한 사전 고정 검증은 아니다.

| 기준 | 2017년만으로 다시 계산 | 2018년에서 |
|---|---|---|
| C5 60일 | 배송 일수 상위 1% 45.5일, 0.1% 104.4일. 60일은 그 사이 | |
| C5 3건 | 2017-09-19를 빼면 한 시간 최대 1건 | 3건 이상인 시간대 0개(헛경고 0). 2건인 시간대 13개라 여유는 1건 |
| C15 경고 3시간 | 평소(그날 지연 중앙값들의 중앙값) 0.26시간의 10배 = 2.6시간 → 시간 단위로 3시간 | 3시간 이상 18일 |
| C15 실패 12시간 | 정할 때 쓴 하루짜리 멈춤 3일(21~23시간)이 모두 2018년이라 2017년만으로는 다시 정할 수 없음. 2017년의 멈춤은 18.7시간 2일, 12.1시간 1일 | 2018년 평가는 순환이라 하지 않음 |
| C16 2배 | 요일 변동(월 중앙값 ÷ 토 중앙값) 1.65배. 2배가 그보다 큰 가장 가까운 정수 | 경고 13일(끝부분 8일 포함) |
| C16 2배와 3배 중 선택 | 2017년 사건(블랙프라이데이 6.1배, 06-21 0.31배, 12-24 0.32배)은 둘 다 잡아 2017년만으로는 고를 근거가 없음. 2배를 고른 근거(05-26·27)는 2018년 | |

C5와 C16 요일 변동, C15 경고선은 2017년만으로도 같은 값이 나왔다. C15 실패선과 C16의 2배 대 3배 선택은 2018년 사건을 보고 정해서, 이 데이터로는 독립적인 평가를 할 수 없다.

## 역할

검사 기준, 처리, 분석 방법의 결정은 작성자가 했다. 조사 쿼리, 검사 코드, 테스트, 분석 코드는 Claude Code가 작성했다. 결정마다 누가 제안하고 누가 정했는지는 `DECISIONS.md`의 '누가' 항목에 있다.

## 다시 돌리기
